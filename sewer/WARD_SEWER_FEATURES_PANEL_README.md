# Ward Sewer Features Panel — `ward_sewer_features_panel_2019_2023.csv`

Generated by `build_ward_year_panel_2019_2023.py`. One row per `(ward, year)` — 25 Toronto wards × 5 years (2019-2023) = **125 rows**, 0 nulls. `ward_id` = `AREA_SHORT_CODE` from `City Wards Data - 4326.geojson`. `ward_year` = `f"ward_{ward_id}_year_{year}"` (e.g. `"ward_13_year_2021"`).

Source datasets (Toronto Open Data): [Sewer Gravity Main](https://open.toronto.ca/dataset/sewer-gravity-mains/), [Sewer Inlets](https://open.toronto.ca/dataset/sewer-inlets/), [Sewer Manholes](https://open.toronto.ca/dataset/sewer-manholes/), [Sewer Outfalls](https://open.toronto.ca/dataset/sewer-outfalls/), [City Wards](https://open.toronto.ca/dataset/city-wards/).

This replaces `ward_sewer_features.csv` (static) and `ward_sewer_features_panel_2019_2022.csv` (where only `avg_pipe_age` varied by year) — both are kept as historical reference, not deleted.

## Methodology: assigning sewer assets to ward

Same approach as `build_ward_sewer_features.py`: for **point assets** (inlets, manholes, outfalls), test whether each point falls inside a ward polygon (`geopandas.sjoin(..., predicate="within")`). For **line assets** (pipes, which can cross a ward boundary), take the pipe's **midpoint** and test which ward polygon contains it.

## Why these features now vary by year

Every pipe, inlet, and manhole has its own real installation date. For a row with a given `ward` and `year`, every feature below (except `dist_to_nearest_outfall_m`) is calculated using **only the pipes/inlets/manholes in that ward whose installation date is on or before that `year`** — anything installed after that `year` is simply left out of the calculation for that row. So the same ward has a different (growing) set of pipes/inlets/manholes feeding into each year's numbers: the 2019 row for a ward only "sees" what was already installed by 2019, the 2020 row "sees" everything installed by 2020 (one more year's worth), and so on through 2023. This replaces the earlier assumption (used in `ward_sewer_features.csv` and `ward_sewer_features_panel_2019_2022.csv`) that these features were static and identical across all years.

## This file uses only `Sewer Gravity Main` (no Trunk Sewer)

Unlike the original `ward_sewer_features.csv` (which unified Gravity Main + Trunk Sewer), this panel uses **only `Sewer Gravity Main`** — same scope decision already made for `fsa_static_sewer_features.csv`, so every column comes from one consistent source dataset.

## Features

| Feature | What it is | How it's calculated |
|---|---|---|
| `avg_pipe_age` | Average age (years) of the ward's pipes installed by that `year`. | For every pipe in the ward with `install_year <= year`, compute `year − install_year`, then average those values. |
| `new_pipe_km` | Kilometers of pipe installed **exactly** in that row's `year` (not cumulative) — a signal of recent infrastructure investment. | Sum of `length_km` for pipes in the ward where `install_year == year` (not `<=`, only pipes installed that specific year). |
| `pct_old_pipe` | Share of the ward's installed-by-then pipe length that has already crossed the "old pipe" age threshold. | Among pipes in the ward with `install_year <= year`: `(length of those with age > 72 years) / (total length of all of them)`. The 72-year threshold is the 75th percentile of age over the whole `Sewer Gravity Main` network citywide (reference year 2026, computed once — see `FSA_INSTALL_DATE_FEATURES_README.md`), reused unchanged across all 5 years. |
| `cumulative_pipe_km` | Total pipe length already installed in the ward as of that `year` — a running total. | Sum of `length_km` for pipes in the ward where `install_year <= year`. Non-decreasing across years within the same ward (verified). |
| `pct_combined_sewer` | Share of the ward's installed-by-then pipe length that is "combined" type (carries both sanitary wastewater and stormwater in the same pipe), vs. "separated" systems. Combined sewers are more prone to backup during heavy storms. | Among pipes in the ward with `install_year <= year`: `(length of combined-type pipes) / (length of combined-type + separated-type pipes)`. `EO` and `FD` pipe types are excluded from this ratio. |
| `avg_pipe_diameter` | Average diameter (mm) of the ward's pipes installed by that `year`. | Mean of the `Diameter` field over pipes in the ward with `install_year <= year`. |
| `pipe_density` | Length of pipe installed by that `year`, per unit area of the ward (km of pipe per km²). | `(sum of lengths, in km, of pipes in the ward with install_year <= year) / ward area (km²)`. |
| `fd_density` | Density of Foundation Drain (FD) pipes installed by that `year`, per km² — pipes connecting house foundation drainage directly to the sewer system, a direct exposure pathway for basements. | `(length, in km, of FD-type pipes in the ward with install_year <= year) / ward area (km²)`. |
| `catch_basin_density` | Number of catch basins (inlets) installed by that `year`, per km² of the ward. | `(count of inlets in the ward with install_year <= year) / ward area (km²)`. |
| `manhole_density` | Number of manholes installed by that `year`, per km² of the ward. | `(count of manholes in the ward with install_year <= year) / ward area (km²)`. |
| `pct_combined_manholes` | Same concept as `pct_combined_sewer`, counted over manholes instead of pipe length. | Among manholes in the ward with `install_year <= year`: `(count of combined-type) / (count of combined-type + separated-type)`. |
| `dist_to_nearest_outfall_m` | Distance (meters) from the ward's centroid to the nearest sewer outfall (where flow exits into a river or the lake). **Does not vary by year.** | Euclidean distance in a metric CRS (EPSG:2952) between the ward's centroid and the closest outfall point — computed once for each ward, since outfalls have no recorded installation date to filter by. Same value repeated in all 5 years for that ward. |

## Assumptions / known limitations

- Pipes/inlets/manholes crossing a ward boundary are assigned using the pipe's midpoint (lines) or the point's exact location (inlets/manholes/outfalls) — same simplification as the original ward pipeline.
- 147 of 164,685 pipes (0.09%), 700 of 173,798 inlets (0.4%), and 156 of 160,640 manholes (0.1%) fell outside all ward polygons (edge of the covered area) and are excluded.
- **`Sewer Inlets` has 15.4% of rows matched to a ward (26,665 of 173,098) with no valid installation date.** Those rows can **never** be counted in `catch_basin_density`, in any year — because there's no date to compare against `install_year <= year`. This is unlike the original static `ward_sewer_features.csv`, which counted every inlet regardless of date, so `catch_basin_density` in this panel is systematically lower than that old static value, even in 2023 (the last year of the range).
- `Sewer Manholes` has only 1.9% nulls in its install date — a much smaller effect on `manhole_density` and `pct_combined_manholes`.
- `Sewer Outfalls` has no installation-date column at all, so `dist_to_nearest_outfall_m` can't vary by year — a real data limitation, not a design choice.
- One `Sewer Gravity Main` row had a corrupted installation date (`"3000-01-01"`, year 3000); it's automatically dropped since `install_year` can't be computed from it, same as any other invalid date.
- This file deliberately excludes `Trunk Sewer` (unlike the original `ward_sewer_features.csv`, which unified it with Gravity Main). This slightly lowers `pipe_density` and `avg_pipe_diameter` vs. a trunk-inclusive version (trunk sewers are the largest-diameter pipes), but keeps every feature derived from one consistent source dataset.

## Validation performed

- 125 rows (25 wards × 5 years), 0 nulls across all 16 columns.
- `cumulative_pipe_km` confirmed non-decreasing across all 25 wards.
- Sanity check: Ward 13 (Toronto Centre, historic downtown) has `pct_combined_sewer` consistently ~57.9-58% with `avg_pipe_age` rising from 79.3 to 82.8 years (2019→2023), vs. Ward 25 (Scarborough-Rouge Park, suburban) at `pct_combined_sewer` = 0% with `avg_pipe_age` from 35.9 to 39.9 years — the same historic downtown-vs-suburb pattern already confirmed in earlier versions of these features.
